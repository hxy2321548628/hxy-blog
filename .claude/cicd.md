# CI/CD 规范


## 1. 统一命令

- 仓库根目录提供 `Taskfile.yml`；本地和 CI 使用相同的 Task 版本与任务入口。
- 必备任务：`install`（按锁文件安装依赖）、`lint`（静态检查）、`test`（自动化测试）、`build`（生成制品）、`check`（汇总合并前检查）。失败必须返回非零状态。
- `task check` 至少执行 `lint`、`test`、`build`；开发者提交前运行它，CI 也调用它。安装与检查不得改写源码或锁文件。
- `dev`、`package`、`smoke`、`deploy` 按需添加；部署任务必须显式指定环境和制品，不得默认部署生产。
- workflow 只负责触发、权限、环境、任务编排和制品传递；可本地运行的构建逻辑写在 Taskfile 或其调用的脚本中。

## 2. 验证与构建

- 所有变更经 PR 合入受保护分支；PR 必须通过名为 `check` 的必需状态检查及项目配置的安全扫描。
- PR 检查执行 `task install` 和 `task check`，不接触生产密钥，也不部署生产。来自 fork 的代码不得在有特权的上下文或可接触敏感资源的自托管运行器上执行。
- 合并后重新验证，再生成不可变制品；记录 commit SHA、构建运行链接、制品版本及摘要。发布和环境晋级使用这份已验证制品，不重新构建。

## 3. 部署与回退

- 项目须写明发布触发方式、目标环境、部署负责人、健康检查和回退步骤。
- 生产部署仅接受受保护来源的已验证制品，并经过生产环境审批；若 GitHub 计划不支持所需审批规则，上线前建立等效门禁。
- 同一环境的部署串行执行，生产部署不得被后续运行自动取消。部署后验证健康状态；失败时停止晋级并回退到上一已验证制品。

## 4. 安全与维护

- 显式设置最小 `permissions`；优先使用 `GITHUB_TOKEN` 和 OIDC 短期凭据，仅在需要的 job 授予写权限或 `id-token: write`。
- 第三方 Action 固定完整 commit SHA；密钥只传给必要的步骤，不进入代码、日志、缓存或制品。可复用工作流默认逐项传递所需密钥。
- 缓存只保存可重建的依赖和中间结果；缓存命中不能代替测试。先记录 job 耗时与缓存命中率，再做并行或缓存优化。
- 重复步骤可用复合 Action，重复流程可用可复用工作流；修改 workflow 时先本地检查，再在 GitHub 验证权限和部署行为。
- 修改门禁、权限或发布流程的 PR 必须说明影响、验证结果和回退方式，并由项目维护者评审。

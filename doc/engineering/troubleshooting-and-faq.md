# 排错记录与常见问题

本文分两部分：上半是 Sprint 0 过程中**真实踩到的坑**及其修复；下半是把这些坑抽象成可复述的问答，便于复习和面试表达。

## 第一部分：真实踩坑记录

### 1. GitHub 免费私有仓库不支持分支保护（403）

**现象**：`gh api` 配置 branch protection 返回 403，提示当前套餐不支持私有仓库的分支保护和 Rulesets。

**根因**：保护规则是付费能力。私有仓库在免费套餐下无法强制阻止直接推送 `main`。

**影响**：“禁止在 main 上开发”这条规范当时**无法被强制**，只能靠自觉和本地 Hook，而本地 Hook 可以被绕过。

**解决**：把仓库从私有改为公开，随后成功配置：

- 必须通过 Pull Request
- 必需状态检查 `check`
- 必须基于最新 `main`
- 线性历史、解决会话
- 禁止强推和删除
- 规则对管理员同样生效

**沉淀的认知**：规范要有**服务端强制**才成立；本地约束只是辅助。

### 2. `go.sum` 缓存路径不匹配导致缓存恢复失败

**现象**：CI 中反复出现非阻断警告：

```text
Restore cache failed: Dependencies file is not found in
/home/runner/work/hxy-blog/hxy-blog. Supported file pattern: go.sum
```

**根因**：`actions/setup-go` 的 `cache: true` 默认在**仓库根目录**查找 `go.sum`，但本项目的 Go 模块在 `src/backend/`：

```text
src/backend/go.sum          ← 依赖清单的真实位置
./go.sum                    ← setup-go 默认查找的位置（不存在）
```

所以不是“缺少 go.sum”，而是**缓存键的查找路径不对**。这解释了为什么这个警告在依赖清单早已提交后依然存在。

**影响**：仅导致 Go 依赖缓存无法命中，每次 CI 都要重新下载模块（浪费时间，不影响正确性）。属于**待修复项**。

**修复方向**（本 PR 只记录，不改工作流）：

```yaml
- uses: actions/setup-go@v5
  with:
    go-version-file: src/backend/go.mod
    cache: true
    cache-dependency-path: src/backend/go.sum   # 显式指定
```

注意前端那一步已经正确处理了同类问题：`setup-node` 显式写了 `cache-dependency-path: src/web/package-lock.json`。Go 这步缺了对应配置——**同一个工作流里两个工具，一个配了一个没配**。

**沉淀的认知**：默认值只在“目录结构符合默认假设”时成立。仓库使用子目录布局时，所有按路径推断的配置都要显式声明。同时，非阻断警告要记录并排期修复，因为警告会训练人忽略 CI 输出。

### 3. GitHub Actions 的 Node.js 20 运行时弃用警告

**现象**：CI 输出 `Node.js 20 actions are deprecated`。

**根因**：某些 Action 的版本仍在 Node 20 运行时上。

**影响**：仅警告，不影响功能。

**处理**：记录为待办，随 Action 版本升级一起解决，而不是为了消警告而随意改版本。CI 中**第三方 Action 必须固定到完整 Commit SHA**（如 `actions/checkout@d23441a4…`），因为标签可能被移动，这是供应链风险。

### 4. 服务器无法访问 github.com

**现象**：从服务器测试访问 `github.com` 超时；但 `ghcr.io` 正常（未登录返回预期的 401，耗时约 0.6 秒）。

**影响**：直接否定了“服务器 git pull 后本地构建”的方案。

**决策**：走 `CI 构建 → GHCR → 服务器拉镜像`。这条实测数据是整个 CD 选型的直接依据。

**沉淀的认知**：架构决策要基于**实测**，不能基于“应该可以”。

### 5. 数据库备份文件名撞名导致无法取回

**现象**：演练时发现同一秒内产生的两份备份文件名相同，COS 端无法区分/取回对应版本。

**根因**：时间戳只精确到秒。

**解决**：时间戳改为 UTC 纳秒格式：

```text
20260930T034110603421034Z-sha-c0e704c6bdba.sql.gz
```

**加固**：上传时使用 `--forbid-overwrite`，从协议层面禁止覆盖已归档备份。

**沉淀的认知**：备份**文件名是标识**。标识一旦可能重复，整套归档就不可信。

### 6. 腾讯云轻量应用服务器不支持实例角色

**现象**：控制台找不到“绑定实例角色”入口，无法按计划给服务器授予 COS 访问权。

**根因**：实例角色（CAM Role for CVM）是标准 CVM 的功能。Lighthouse 的 CAM 管理指的是“谁可以管理这台机器”，不是“这台机器拥有什么身份”。

**解决**：改用专用 CAM 子用户（仅编程访问）+ 最小权限策略，密钥以 `root:root 0600` 保存在服务器。

**沉淀的认知**：云产品的同名能力可能语义不同。选型阶段要确认“这台机器能否获得自动轮换的临时凭证”。

### 7. 镜像在 Runner 上能跑，但没验证过目标服务器

**现象**：容器基线 PR 通过 CI，但只证明了“能在 GitHub Runner 上构建和运行”。

**风险**：真正的问题是“能否在生产机拉取并跑起来”，这两件事完全不同（网络、架构、资源、Docker 版本都会不同）。

**解决**：增加**目标机冒烟测试**：

- 服务器从 GHCR 匿名拉取镜像（验证真实网络链路）。
- 用独立项目名、临时卷、临时密码起栈。
- 端口只绑 `127.0.0.1`。
- 连续观察约 9 小时，确认 `healthy` 且重启次数为 0。
- 测完删除全部临时资源。

**资源实测**（对 2C2G 很有参考价值）：

| 服务 | 内存占用 |
| --- | --- |
| MySQL | 约 416 MiB |
| Go API | 约 3.4 MiB |
| Nginx Web | 约 3.2 MiB |

**沉淀的认知**：CI 绿 ≠ 生产能跑。中间必须有一次**真实目标机验证**。

### 8. 用“发布成功”代替回滚演练

**现象**：CD 完成后所有发布都是成功的，但回滚代码路径**从未被执行过**。

**风险**：回滚是最需要验证、却最容易从未验证的分支。它能工作时你看不见，它不能工作时你在故障中才发现。

**解决**：按 ADR-0005 执行受控演练——故意注入一个健康检查失败的候选版本，确认脚本自动恢复上一版本：

- 部署脚本正确返回失败
- `previous.env` 被恢复，上一版本容器重新健康
- MySQL 容器与持久化卷未受影响
- 演练临时文件清理干净

**沉淀的认知**：**不可达的代码路径等于不存在**。回滚、恢复、降级都必须演练。

### 9. 定时任务与部署并发写同一份状态

**风险场景**：每日定时备份与部署触发的前置备份可能同时操作同一个 MySQL 容器和备份目录，导致文件竞争或备份不完整。

**解决**：两个脚本共用同一把 `flock` 锁：

```bash
exec 9>"${BACKUP_LOCK}"
flock -n 9 || fail '已有数据库备份正在执行'
```

部署脚本另有一把独立锁 `/run/lock/hxy-blog-deploy.lock`，保证**同一时间只有一个部署**。

**沉淀的认知**：单机上任何会修改共享状态的定时任务，都要有锁。

### 10. 文档状态与实现状态脱节

**现象**：Sprint 0 后期 Backlog 仍显示 MySQL、CD、服务器部署未完成，但实际早已完成。

**风险**：文档一旦失真，人和 AI 都会基于错误前提做决策（例如重复实现已有能力）。

**解决**：Sprint 收口时同步 [`backlog.md`](../product/backlog.md) 与 [`sprint-0-acceptance.md`](./sprint-0-acceptance.md)，并为每一行附**可复现的证据**（CI 运行 ID、提交 SHA）。

**沉淀的认知**：验收记录的价值在于**证据可复现**，而不在于写了“通过”。

## 第二部分：常见问题（FAQ）

### 基础概念

**Q1：GHCR 是什么？和 Docker Hub 有什么区别？**
GHCR（GitHub Container Registry）是 GitHub 提供的容器镜像仓库，地址前缀 `ghcr.io`。功能上与 Docker Hub 同类，区别在于它与仓库、Actions、权限体系天然集成，`GITHUB_TOKEN` 即可推送，权限通过 `packages: write` 控制。

**Q2：Tag 和 Digest 有什么区别？为什么部署要用 Digest？**
Tag 是可变指针（`mysql:8.0` 明天可能指向不同内容），Digest 是内容的 SHA-256 指纹，内容变则 Digest 必变。生产要**可复现**，所以必须锁 Digest。本项目的 `deploy.sh` 会强制校验 `^sha256:[0-9a-f]{64}$`。

**Q3：CI 和 CD 的边界在哪？**
CI 回答“这次改动合格吗”，产出判断；CD 回答“合格改动如何上线”，产出运行中的版本。本项目 CI 完全不接触生产，CD 只接受通过 CI 的提交。

**Q4：`workflow_run` 和直接 `push` 触发 Release 有什么差别？**
`push` 触发会让镜像构建与 CI 并发，CI 还没结论就开始构建。`workflow_run` 能等到 CI 完成，并拿到**精确的上游提交 SHA**和结论，从而保证“只构建已通过 CI 的那个提交”。

### 关于选型

**Q5：为什么不直接在本地打包镜像 SCP 上传？**
因为发布就依赖你的电脑状态：可能有未提交代码、架构可能不一致、无法证明线上镜像对应哪个提交、换电脑要重建环境、每次要传完整镜像包。SCP 在本项目中仅作为 **GHCR 长时间不可用时的应急路径**，且仍要走同一个固定部署入口。

**Q6：为什么不在生产服务器上 `git pull` 然后构建？**
占用 2C2G 的 CPU/内存和磁盘、需要装 Go/Node 构建依赖、污染生产环境；而且实测这台服务器访问 `github.com` 会超时。构建必须放在 GitHub 托管 Runner。

**Q7：为什么不用 Self-hosted Runner？**
仓库是公开的。自托管 Runner 意味着来自不可信 PR 的工作流代码可能接触到生产网络和凭据。GitHub 官方也不建议公开仓库使用自托管 Runner。

**Q8：镜像为什么设为公开？**
源码本身已公开，镜像中不含任何密钥（密钥只在服务器运行时注入）。公开后服务器可匿名拉取，无需长期保存 `read:packages` Token，减少凭据管理面。

**Q9：为什么基础镜像要固定 Digest？**
同一 Tag（如 `alpine:3.22`）在不同时间可能指向不同内容。固定 Digest 后，同样的提交在任何时间构建都得到**内容一致**的产物，这是可复现构建的前提。

**Q10：为什么前端最终选了 React SPA 而不是 Next.js SSR？**
SSR 对 SEO 和分享卡片更好，但生产要额外跑 Node.js，2C2G 上运维成本显著上升。最终选择 SPA，把“公开文章首屏 HTML 不含正文、SEO 较弱”**明确写进 ADR 作为已接受取舍**，而不是假装没有代价。

**Q11：为什么用 Goose 而不用 GORM AutoMigrate？**
AutoMigrate 会创建缺失的表/字段/索引并做部分类型调整，但为了保护数据**不会删除**废弃字段；而且没有迁移版本历史、没有自动 down、拆表和数据回填难以表达、Schema 变化藏在 Go Model 里不方便在 PR 中审查真实 SQL。它适合开发期快速迭代，不适合可审计的生产 Schema 管理。因此：GORM 负责运行时 CRUD，Goose 负责版本化 up/down。

### 关于部署与回滚

**Q12：部署失败时会自动执行数据库 `down` 吗？**
不会，这是刻意的。新版本可能已经写入了旧 Schema 无法表达的数据，自动 `down` 可能直接毁数据。规则是：**应用镜像自动回滚，数据库回退必须人工评估**。Schema 变更遵循“先扩展、再迁移、后收缩”。

**Q13：为什么备份必须在迁移之前？**
如果先迁移再备份，一旦迁移改坏数据，备份里已经是坏数据。顺序必须是：确保 MySQL 健康 → 备份 → 迁移 → 切换应用。

**Q14：手动回滚怎么做？**
服务器的当前/上一版本记录在两个环境文件里：

```bash
sudo cat /opt/hxy-blog/release.env      # 当前
sudo cat /opt/hxy-blog/previous.env     # 上一版（回滚基线）

# 回滚 = 把上一版环境文件装回当前位，再用该文件重建服务
sudo install -o root -g root -m 600 /opt/hxy-blog/previous.env /opt/hxy-blog/release.env
sudo docker compose --project-name hxy-blog-production \
  --env-file /etc/hxy-blog/runtime.env \
  --env-file /opt/hxy-blog/release.env \
  --file /opt/hxy-blog/compose.yaml \
  up -d --no-build --wait --wait-timeout 120
```

因为版本记录就是“镜像 Digest + Commit”，回滚不需要重新构建任何东西。

**Q15：首次部署失败会怎么处理？**
没有 `previous.env` 可恢复，因此脚本执行 `down --remove-orphans` 停止应用栈，但**保留 MySQL 命名卷**，数据不会丢。

**Q16：部署期间服务会中断吗？**
V1 是单实例替换发布，容器切换期间有短暂不可用。这是为个人博客刻意接受的代价：不为一个低流量站点提前引入双实例流量编排。

**Q17：GitHub Actions 能拿到服务器的数据库密码吗？**
不能。GitHub 只保存 `DEPLOY_HOST`、`DEPLOY_PORT`、`DEPLOY_USER`、`DEPLOY_SSH_KEY`、`DEPLOY_HOST_KEY`。数据库密码、JWT 密钥、COS 凭据只在服务器 `/etc/hxy-blog/` 下，Actions 从不读取。

### 关于服务器与备份

**Q18：为什么端口要绑 `127.0.0.1` 而不是 `0.0.0.0`？**
`0.0.0.0` 表示监听所有网卡，公网可直接访问。绑 `127.0.0.1` 让服务**根本不存在于公网**，比任何防火墙规则都更彻底。开发环境同样处理数据库端口。

**Q19：备案期间真的不能用公网 IP 访问吗？**
不能。腾讯云要求备案审核期间公网域名和公网 IP 都不可访问网站内容，否则可能被驳回。备案期用服务器本机 `curl` 或 SSH 隧道验证。

**Q20：COS 备份为什么没有删除权限？**
因为“能删备份的凭据”会削弱备份的意义。CAM 策略只授予上传/读取/分片相关权限，资源限定到 `mysql/*`；**保留与删除交给 COS 生命周期规则**（90 天）。这样即使服务器被攻破，历史备份也删不掉。

**Q21：备份文件为什么要在上传后立刻回读？**
为了在同一次任务里证明“**可上传**”并且“**可恢复**”。很多备份事故的真实形态是：文件安静地躺了半年，出事时发现读不回来。

**Q22：恢复演练为什么不直接恢复到生产库？**
破坏性操作不能被脚本自动化。演练固定恢复到隔离库 `hxy_blog_restore_drill`，校验完成后自动删除，生产库不受影响。生产恢复永远是人工故障处理流程。

**Q23：2C2G 跑得动吗？**
实测可以：MySQL 约 370–420 MiB、API 约 2–4 MiB、Web 约 3–7 MiB，加上系统与约 1.9 GiB Swap 有充足余量。前提是**必须设 `mem_limit` 和日志轮转**，否则写满内存或磁盘只是时间问题。

### 关于流程

**Q24：为什么 `main` 一次只能有一个部署？**
避免两个部署同时修改 Compose 状态或数据库 Schema。用 `flock` 保证互斥，失败方直接报“已有部署正在执行”而不是排队等待（排队会导致发布延迟不可预测）。

**Q25：`make check` 和 CI 是什么关系？**
CI 的 `check` Job 直接调用 `make check`，两者同源。这样不存在“本地过了 CI 不过”的情况。本地跑 `make check` 就是在本地跑 CI 的门禁。

**Q26：PR 的检查明明通过了，为什么不能合并？**
GitHub 的 “Require branches to be up to date” 规则要求检查基于最新 `main`。如果期间有别的 PR 合入，需要更新分支并重新触发检查。

**Q27：AI 完成的提交需要人做什么？**
按风险分级：低风险变更（文案、样式、无行为重构）AI 自验后可提 PR；中风险（新 API、新依赖、可回滚迁移）需人工代码评审；高风险（鉴权、权限、删数据、不可逆迁移、生产发布）需人工设计确认 **加** 发布批准。

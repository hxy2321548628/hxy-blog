# AI Coding 工程流程

## 目的

让人和 AI 在相同上下文、相同质量门禁下小步交付，减少“代码能跑，但不符合需求”的返工。

## 五层工程闭环

| 层 | 产物 | 质量门禁 |
| --- | --- | --- |
| 意图 | 用户故事、非目标 | 产品负责人确认价值 |
| 规约 | 验收标准、ADR、API/Schema 契约 | 边界和异常路径可验证 |
| 实现 | 最小代码变更 | 不超出故事范围 |
| 验证 | 自动化测试、lint、build | `make check` 通过 |
| 交付 | PR、发布记录、回滚方案 | 人工复核高风险变更 |

## 敏捷节奏

- Sprint 长度：1 周。
- 每周最多承诺 3–5 个可独立演示的故事。
- 每个故事依次经过：澄清 → 写失败测试 → 最小实现 → 重构 → PR → 演示。
- Sprint 评审只看可运行的产物；未通过验收的故事回到 Backlog。
- 回顾每次只选一个可执行的流程改进项。

## Definition of Ready

故事进入 Sprint 前必须同时满足：

- 用户与价值明确。
- 包含 2–5 条可观测的验收标准。
- 非目标和外部依赖已写明。
- 可在 1–2 天内完成；超出则先拆分。
- 对数据迁移、鉴权、丢数据风险有明确判断。

## Definition of Done

- 所有验收标准已通过测试或可重复演示。
- 新代码通过 `make check`。
- 文档、API 契约和迁移与代码同步。
- 日志中无敏感信息，新配置已加入 `.env.example`。
- PR 说明风险、验证证据和回滚方式。

## 给 AI 的任务卡模板

```markdown
# 目标
作为 <用户>，我希望 <能力>，以便 <价值>。

## 范围
- 需要：
- 不需要：

## 验收标准
- Given ... When ... Then ...

## 约束
- 性能/安全/兼容性：

## 验证命令
- `make check`
```

AI 开始编码前必须输出：理解的目标、假设、最小方案、验证方法。若多种解释会改变数据模型、API 或用户体验，先询问，不暗自选择。

## 风险分级

- 低：文案、样式、无行为变化的重构。AI 自验后可提交 PR。
- 中：新 API、新依赖、可回滚迁移。需人工代码评审。
- 高：鉴权、权限、删数据、不可逆迁移、生产发布。需人工设计确认和发布批准。

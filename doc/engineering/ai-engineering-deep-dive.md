# AI 项目工程化深度解析

本文解释 Sprint 0 为什么要把“人 + AI”当作一套工程系统来建设，以及每个约束文件解决什么真实问题。目标不只是“让 AI 写出代码”，而是让**产出可以被重复、被审查、被回滚**。

## 1. 问题：AI 编码的真实风险不是写错代码

AI 写代码很快，真正的风险来自另外三件事：

| 风险 | 典型表现 | 后果 |
| --- | --- | --- |
| 上下文漂移 | 换一个会话，AI 不知道上次定了什么规范 | 同一个项目出现两套风格 |
| 越权决策 | AI 自行选定框架、镜像、部署平台 | 技术选型既成事实，无法追溯 |
| 验证缺失 | 只跑通“看起来能跑”，没跑门禁 | 缺陷在合并后才暴露 |

Sprint 0 的第一个版本就踩到了第二条：AI 直接选定了 Go 标准库、`sqlc`、GitHub Actions，并提交到了尚未评审的 `main`。随后项目负责人指出“技术选型没有跟我确认”，这批提交被追认为**待评审的工程草案**，流程重排。

这是本仓库最值得记住的一个教训：

> AI 默认会把“我推荐的”当成“已确认的”。必须用文件和流程强制它区分这两者。

## 2. 第一层约束：意图与边界

### 2.1 `AGENTS.md`：唯一入口

`AGENTS.md`（`CLAUDE.md` 是指向它的软链接）是所有 AI 工具进入项目的第一份文件。它不写实现细节，只回答四个问题：

- 这个项目要做什么、不做什么（2C2G 单机、模块化单体）。
- 技术基线是什么（Go 1.25 / React + TS + Vite / MySQL / Docker Compose）。
- 必读文件在哪里。
- 目录边界在哪里（`src/backend`、`src/web`、`doc/`、`deploy/`）。

为什么必须有一个唯一入口？因为 AI 每次会话的上下文是全新的。把稳定约束放在仓库文件里，而不是留在聊天记录里，才能真正复现。

> 判断标准：如果聊天记录被清空，AI 还能不能按同样方式工作？不能，就说明约束没有沉淀到文件。

### 2.2 `.claude/constitution.md`：技术章程

章程规定工程价值观，例如“优先标准库”“不提前搭建未被需求驱动的抽象”“迁移必须可回滚”“日志不得含敏感信息”。这些是**跨故事长期有效**的判断准则。

### 2.3 `.claude/code-style.md`、`.claude/git-command.md`：可执行的规范

规范的价值在于**可检查**。`git-command.md` 中的规则直接对应远程保护设置和 CI：

- 禁止直接向 `main` 推送 → GitHub 分支保护规则。
- 提交信息用 Conventional Commits → 便于生成变更历史。
- 提交前运行 `make check` → CI 的必需状态检查。

## 3. 第二层约束：把决策写成 ADR

`doc/architecture/` 下的 ADR（Architecture Decision Record）记录“为什么这样选”，这是 AI 最容易跳过、也最需要留痕的部分。

Sprint 0 共固化 6 份决策：

| ADR | 决策主题 | 关键取舍 |
| --- | --- | --- |
| 0001 | 初始架构 | 2C2G 单机、模块化单体，不引入微服务 |
| 0002 | 媒体存储 | 直接上腾讯云 COS，不做“本地卷再迁移” |
| 0003 | 应用技术栈 | Gin + GORM + Goose、React SPA、Axios、Redux Toolkit |
| 0004 | 管理员鉴权 | 短期 Access JWT（内存）+ 可轮换 Refresh Token（HttpOnly Cookie） |
| 0005 | 持续交付 | GHCR + 受限 SSH 部署 + 自动回滚 |
| 0006 | 异地备份 | COS + SSE-COS AES-256 + 90 天保留 |

ADR 的固定结构：状态 → 背景 → 问题与动机 → 范围（内/外）→ 决策 → 安全考虑 → 测试与验收 → 监控 → 回滚计划 → 风险 → 备选方案 → 后果。

其中三个小节是最容易被忽略、但最能防止 AI 过度设计的：

- **范围外**：明确写“不做 Kubernetes、不做蓝绿发布、不做自动 down migration”，AI 就不会顺手加。
- **备选方案**：写下被否决的方案和理由。否则下次对话 AI 会重新提名它们，浪费一轮。
- **已关闭的实施参数**：把镜像 Digest、目录、用户名、域名等硬参数钉死在文档里。

## 4. 第三层约束：把人机协作写成流程

`doc/engineering/ai-coding-workflow.md` 定义了五层闭环：

```text
意图 → 规约 → 实现 → 验证 → 交付
 用户故事  验收标准/ADR  最小变更  make check  PR/回滚方案
```

两个关键机制：

### 4.1 AI 执行契约（开工前必须复述）

AI 在编码前必须输出：目标、非目标、假设、最小方案、验证方法。若存在多种解释会改变数据模型、API 或用户体验，**必须先问，不许暗自选择**。

这条规则直接对应 Sprint 0 中“Next.js vs React SPA”的分叉：先解决架构分叉，再动代码。

### 4.2 风险分级

| 级别 | 内容 | 需要的人工动作 |
| --- | --- | --- |
| 低 | 文案、样式、无行为重构 | AI 自验后可提 PR |
| 中 | 新 API、新依赖、可回滚迁移 | 人工代码评审 |
| 高 | 鉴权、权限、删数据、不可逆迁移、生产发布 | 人工设计确认 + 发布批准 |

“生产发布”被归入高风险，因此在 Sprint 0 中演化为 GitHub `production` Environment 的**人工批准门禁**——这是流程约束在流水线中的物理落地。

## 5. 第四层约束：让验证不可绕过

人和 AI 都可能忘记跑测试，所以质量门禁必须放在**无法跳过**的位置：

1. `make check`：本地一键校验（格式、vet、单测、前端 lint 与构建、Compose 配置校验）。
2. PR CI：必需状态检查名为 `check`，由分支保护强制。
3. 合并后 CI：再跑一次 `main`，捕捉合并结果引入的问题。

`make check` 的实际内容：

```bash
check: fmt-check vet test check-web container-config container-production-config check-deploy
```

关键点：**本地命令与 CI 命令同源**。CI 不写另一套逻辑，只调用 `make check`，避免“本地过了 CI 不过”。

## 6. 反面模式清单（本仓库亲身经历）

| 反面模式 | 发生过的表现 | 现在的对策 |
| --- | --- | --- |
| AI 单方面决策 | 直接选定技术栈并提交 `main` | 技术选型必须经确认后写入 ADR |
| 把推荐当确认 | “建议使用 COS”被当作“已确认使用 COS” | 每次决策结尾明确请求确认 |
| 只验证构建不验证运行 | 镜像在 Runner 上能跑，但服务器未验证 | 加“目标机冒烟测试”环节 |
| 用成功发布代替回滚演练 | 发布全绿，回滚代码从未执行 | ADR-0005 要求注入失败版本演练 |
| 文档与实现脱节 | Backlog 仍显示 MySQL/CD 未完成 | Sprint 收口时同步 Backlog 与验收记录 |

## 7. 可以复用到其他项目的做法

1. 先建**约束文件**，再写第一行代码。
2. 每个技术分叉：给选项 → 列代价 → 请求确认 → 写 ADR。
3. 让本地校验命令与 CI 命令完全一致。
4. 高风险动作（发布、删数据、改权限）必须有人工门禁，而不是靠自觉。
5. 每个 Sprint 结束写验收记录，并附**可复现的证据编号**（CI 运行 ID、提交 SHA）。
6. 把踩过的坑写进文档，否则同样的坑会在下个 Sprint 重现。
